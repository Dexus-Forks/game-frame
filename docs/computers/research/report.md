# Report: game platforms and CPUs

An exact reimplementation of a game from any of these machines depends on three facts to settle first. It needs the CPU family and its arithmetic quirks. It needs the memory and banking state that was live when the code ran. It needs the timing the game was written against, which on 8-bit machines and early consoles is part of the game logic itself. **Eleven CPU families cover almost every platform in scope**: the 8080/Z80/SM83 line, the 6502 line, the 6809, the 68000, the TMS9900, the CP1600, x86, ARM, MIPS, SuperH and PowerPC, plus a few one-off co-processors such as the Cell SPU and the Jaguar's RISC cores. Ghidra builds in most of them. Unicorn 2 covers only the 32-bit and 64-bit families (68000, ARM, MIPS, PowerPC, x86) and has no 8-bit CPU at all. Capstone fills part of the 8-bit gap with its MOS65XX and M680X modes but has no Z80. **Ghidra's 6502 ADC p-code ignores decimal mode and computes the overflow flag wrongly**, so p-code emulation cannot serve as ground truth for 6502 games. The platforms themselves split into four groups with different first steps. On 8-bit home computers the loader and the frame timing come first. On 16/32-bit home computers the custom chips come first, because many games bypass the OS. On the PC and Mac the executable format of each era decides the loader and the tool chain. On consoles from the Xbox 360 onward a decrypted executable and a community Ghidra loader come before any analysis.

In this report, "(not confirmed)" marks a fact that the source page supports but that lacks a second confirmation. Treat it as a lead to check before relying on it.

## Eleven CPU families decide the tools and the arithmetic traps

The CPU family sets the endianness, the disassembler, the emulator core that can produce ground truth, and the arithmetic a port must copy. **Every 8-bit family in scope is little-endian except the 6809. Every 16-bit console CPU except x86 is big-endian.** So a data-file decoder must follow the byte order of the machine that wrote the file. Tool support below reflects the Ghidra master tree (release tag `Ghidra_12.1.4_build`), Unicorn master (release 2.1.4) and Capstone's `next` branch (release 6.0.0-Alpha11) ([Ghidra processors](https://github.com/NationalSecurityAgency/ghidra/tree/master/Ghidra/Processors); [Unicorn headers](https://github.com/unicorn-engine/unicorn/tree/master/include/unicorn); [capstone.h](https://github.com/capstone-engine/capstone/blob/next/include/capstone/capstone.h)).

### What each family looks like in game code

The **Z80** launched in July 1976 and runs Intel 8080 code. It adds an alternate register set (AF', BC', DE', HL'), index registers IX and IY, and the I and R registers. Its undocumented instructions include the 8-bit halves of IX and IY ([Wikipedia: Zilog Z80](https://en.wikipedia.org/wiki/Zilog_Z80)). Ghidra's Z80 spec defines those IXL/IXH/IYL/IYH halves ([z80.slaspec](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/Z80/data/languages/z80.slaspec)). The Game Boy's **Sharp SM83** is a cut-down relative with registers AF, BC, DE, HL, SP and PC, and flags Z, N, H and C in bits 7 to 4. Only DAA reads N and H ([Pan Docs: CPU Registers and Flags](https://gbdev.io/pandocs/CPU_Registers_and_Flags.html)). The Game Boy Advance carries both an ARM7TDMI and an SM83 for older cartridges ([Copetti: Game Boy Advance](https://www.copetti.org/writings/consoles/game-boy-advance/)).

The **6502** appeared in September 1975 with 8-bit A, X, Y and S registers, a status register P and a 16-bit PC. Zero page ($00–$FF) takes a one-byte address and runs faster. The stack is fixed at $0100–$01FF ([Wikipedia: MOS Technology 6502](https://en.wikipedia.org/wiki/MOS_Technology_6502)). The NMOS part leaves 105 of 256 opcodes undefined. Its `JMP ($xxFF)` indirect bug was fixed in the 65C02. The 6507 (Atari 2600) has 8 KB of address space and no interrupts, and the 6510 (C64) adds an I/O port at $0000/$0001 ([Wikipedia: MOS Technology 6502](https://en.wikipedia.org/wiki/MOS_Technology_6502)). The NES 2A03 is a 6502 core "lacking decimal mode" with an APU and OAM DMA at $4014; the PAL RP2A07 uses a different clock divider ([NESdev Wiki: 2A03](https://www.nesdev.org/wiki/2A03)). The PC Engine's **HuC6280** is a 65C02-style core with extra instructions, an MMU that maps 64 KB onto 2 MB, a timer and a PSG ([Wikipedia: Hudson Soft HuC6280](https://en.wikipedia.org/wiki/Hudson_Soft_HuC6280)). The **65C816** (1985) resets into a 65C02-like emulation mode. In native mode the m and x flags set accumulator and index widths. Addresses become 24-bit with DB and DP registers; the SNES 5A22 is based on it ([Wikipedia: WDC 65C816](https://en.wikipedia.org/wiki/WDC_65C816)). The same opcode bytes decode differently by those flags, so a disassembler must track REP and SEP state. A wrong guess produces garbage after the first immediate operand.

The **6809** (1978) joins A and B into a 16-bit D, has X, Y, U and S, an 8-bit direct page register and an 8x8 hardware multiply. Its PC-relative addressing suits position-independent code. It ran the Vectrex, Williams arcade games, the Dragon and the CoCo, and the Hitachi 6309 adds registers, block moves and division ([Wikipedia: Motorola 6809](https://en.wikipedia.org/wiki/Motorola_6809)). Ghidra describes it as big-endian ([6800.ldefs](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/MC6800/data/languages/6800.ldefs)).

The **68000** (September 1979) has eight 32-bit data registers and eight address registers, with A7 split into user and supervisor stack pointers. It has a 16-bit ALU, a 24-bit address bus, an X (extend) flag, MULU/MULS, DIVU/DIVS, BCD instructions and an address-error exception. It ran the Mega Drive (7.6 MHz), the Saturn's sound CPU, the Neo Geo, the Jaguar, the Amiga, the Atari ST, the X68000 and boards such as System 16 and CPS-2 ([Wikipedia: Motorola 68000](https://en.wikipedia.org/wiki/Motorola_68000)).

The **TMS9900** (June 1976) is a 16-bit big-endian CPU with only PC, WP and ST on chip. Its sixteen general registers live in RAM at the workspace pointer, and BLWP saves WP, PC and ST into workspace registers 13 to 15 ([Wikipedia: TMS9900](https://en.wikipedia.org/wiki/Texas_Instruments_TMS9900)). Register reads in its disassembly are memory reads, so tracing a function means tracing the workspace RAM. The **CP1600** (February 1975) addresses only 16-bit words and uses 10 bits of each opcode. R7 is the program counter, R6 the stack pointer, and SDBD builds a 16-bit operand from two 10-bit ROM reads. Ghidra describes it as `CP1600:BE:16:default` ([Wikipedia: CP1600](https://en.wikipedia.org/wiki/General_Instrument_CP1600); [CP1600.ldefs](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/CP1600/data/languages/CP1600.ldefs)).

On **ARM**, nearly every 32-bit instruction carries a 4-bit condition. Thumb code is 16-bit with eight registers and no conditional execution, and the two mix in one program ([Copetti: Game Boy Advance](https://www.copetti.org/writings/consoles/game-boy-advance/)). The early Archimedes ARM2 and ARM3 use a 26-bit address mode with the flags in R15. Old Archimedes games depend on it. On **MIPS**, the PlayStation's R3000A-compatible core at 33.87 MHz has no FPU, a fixed-point GTE, a load delay slot and a branch delay slot ([Copetti: PlayStation](https://www.copetti.org/writings/consoles/playstation/)). The N64's VR4300 is MIPS III and always runs in kernel mode ([Copetti: Nintendo 64](https://www.copetti.org/writings/consoles/nintendo-64/)). The PS2's R5900 adds 128-bit MMI SIMD and two vector units ([Wikipedia: Emotion Engine](https://en.wikipedia.org/wiki/Emotion_Engine)). **SuperH** (1992) uses fixed 16-bit instructions and one branch delay slot. The SH-2 ran the Saturn, 32X and CPS-3, and the SH-4 the Dreamcast ([Wikipedia: SuperH](https://en.wikipedia.org/wiki/SuperH)). On **PowerPC**, the GameCube's Gekko adds about 50 paired-single instructions, and the Wii's Broadway and Wii U's Espresso descend from it ([Wikipedia: Gekko](https://en.wikipedia.org/wiki/Gekko_(processor))). The Xbox 360's Xenon has three in-order big-endian cores with VMX128 ([Wikipedia: Xenon](https://en.wikipedia.org/wiki/Xenon_(processor))). The PS3's Cell pairs one PPE with SPUs that have their own 128-bit ISA, 256 KiB local store and DMA-only access to main memory ([Wikipedia: Cell](https://en.wikipedia.org/wiki/Cell_(processor))). The Jaguar's Tom and Jerry are 32-bit RISC cores at 26.591 MHz with 4 KB and 8 KB of local RAM. A memory controller flaw makes running their code from main RAM awkward, which pushed developers back to the 68000 ([Wikipedia: Atari Jaguar](https://en.wikipedia.org/wiki/Atari_Jaguar)). Tom has two banks of thirty-two 32-bit registers (not confirmed) ([Jagdox general](https://www.mulle-kybernetik.com/jagdox/general.html)).

Unicorn 2 offers ten architectures, all based on QEMU targets ([unicorn.h](https://github.com/unicorn-engine/unicorn/blob/master/include/unicorn/unicorn.h); [qemu/target](https://github.com/unicorn-engine/unicorn/tree/master/qemu/target); [Unicorn README](https://raw.githubusercontent.com/unicorn-engine/unicorn/master/README.md)). QEMU's MIPS headers define `CPU_R5900`, but Unicorn's CPU table has no R5900 entry ([mips-defs.h](https://github.com/unicorn-engine/unicorn/blob/master/qemu/target/mips/mips-defs.h); [translate_init.inc.c](https://github.com/unicorn-engine/unicorn/blob/master/qemu/target/mips/translate_init.inc.c)). For the GBA, the ARM946 or TI925T models are the nearest to the ARM7TDMI. Unicorn emulates CPUs only, so any function that touches custom chips needs stubs. For CPUs Unicorn lacks, MAME's m6809, g65816, tms9900, cp1610, jaguar and m68000 core files carry `license:BSD-3-Clause` headers, though MAME as a whole is GPL-2.0 ([MAME COPYING](https://github.com/mamedev/mame/blob/master/COPYING); [mame/src/devices/cpu](https://github.com/mamedev/mame/tree/master/src/devices/cpu)). Those BSD and MIT cores fit beside GameFrame's Apache-2.0 code. GPL emulators remain usable as external tools. [TomHarte/CLK](https://github.com/TomHarte/CLK) (MIT) is a multi-system alternative, and [ares](https://github.com/ares-emulator/ares) covers many consoles.

### Arithmetic that breaks a bit-exact port

**Ghidra's 6502 `ADC` is not exact.** The spec reads `C = carry(A, op1); A = A + op1 + tmpC; resultFlags(A); V = C;`. It has no decimal path, it leaves the incoming carry out of the carry-out test, and it copies V from C instead of computing signed overflow ([6502.slaspec lines 127–138](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/6502/data/languages/6502.slaspec#L127-L138)). Decimal mode matters: $99 + $01 gives $00 with carry set in BCD and $9A in binary ([Wikipedia: MOS Technology 6502](https://en.wikipedia.org/wiki/MOS_Technology_6502)). The NES 2A03 has no decimal mode, so the same code gives different results on a stock 6502 ([NESdev Wiki: 2A03](https://www.nesdev.org/wiki/2A03)). Ground truth for 6502 code must therefore come from a tested core such as py65, mos6502, MAME or floooh/chips. The NMOS flag behaviour in decimal mode (N, V and Z) still needs a primary source.

Other families have their own traps. Ghidra's Z80 spec implements DAA in full, using N to tell addition from subtraction ([z80.slaspec line 1234](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/Z80/data/languages/z80.slaspec#L1234)). The 8080's DAA is defined only after addition, and the Z80 has no multiply ([Wikipedia: Zilog Z80](https://en.wikipedia.org/wiki/Zilog_Z80)). The SM83 sets carry on a subtraction borrow, as the Z80 and x86 do, which is the reverse of the 6502 and ARM ([Pan Docs](https://gbdev.io/pandocs/CPU_Registers_and_Flags.html)). The 68000's ABCD, SBCD and NBCD use the separate X flag ([Wikipedia: Motorola 68000](https://en.wikipedia.org/wiki/Motorola_68000)). The ARM7TDMI has no hardware divide. GBA games call the BIOS for division, square root and arctangent ([Copetti: Game Boy Advance](https://www.copetti.org/writings/consoles/game-boy-advance/)). Games on the 6502, Z80, SM83 and ARM7 call software multiply and divide routines. Those routines are the functions to emulate for exact results. The SH-1 traps on the SH-2's 64-bit multiplies ([Wikipedia: SuperH](https://en.wikipedia.org/wiki/SuperH)). The PS1 has only fixed point ([Copetti: PlayStation](https://www.copetti.org/writings/consoles/playstation/)), while the N64 FPU follows IEEE 754 ([Copetti: Nintendo 64](https://www.copetti.org/writings/consoles/nintendo-64/)). The PS2's EE FPU "isn't IEEE 754 compliant" ([Wikipedia: Emotion Engine](https://en.wikipedia.org/wiki/Emotion_Engine)). PCSX2's developers report results that differ from x86 by a few bits. Full accuracy would need a slow software FPU ([PCSX2: Nightmare on Floating-Point Street](https://pcsx2.net/blog/2006/nightmare-on-floating-point-street); [PCSX2: What's clamping](https://pcsx2.net/blog/2009/whats-clamping-why-do-we-need-it)). Their documents liken PS2 add and subtract to SSE round-toward-zero without INF or NaN ([PCSX2 wiki VU documentation](https://wiki.pcsx2.net/Special:MobileDiff/38317)). Cell SPU single precision rounds toward zero, treats denormals as zero and has no INF or NaN (not confirmed) ([IBM Cell SDK 3.0](https://arcb.csc.ncsu.edu/~mueller/cluster/ps3/SDK3.0/docs/accessibility/sdkpt/cbet_3codemapeqv.html)). Original SPEs give about 1.8 GFLOPS in double precision each ([Wikipedia: Cell](https://en.wikipedia.org/wiki/Cell_(processor))). A port of PS2 or SPU float code that uses host IEEE floats will drift, so it needs a software float model. Gekko paired-single results depend on the quantised load and store (GQR) setup, which Dolphin's code should confirm. On x86, Turbo Pascal's 6-byte Real and each compiler's calling convention set the rules a PC port must copy ([Turbo Pascal](https://en.wikipedia.org/wiki/Turbo_Pascal)).

## Eight-bit home computers tie game logic to the frame and the loader

Two CPU families cover almost every 8-bit home computer. The Z80 runs the ZX81, Spectrum, CPC, MSX, PC-8801 and X1. The 6502 family runs the BBC Micro and Electron, VIC-20, C64, Atari 8-bit, Oric and Apple II. The 6809E runs the Dragon and CoCo. **Exact timing matters most on four machines**: the Spectrum (contended memory), the C64 (VIC-II badlines and raster interrupts), the Atari (ANTIC DMA and display list interrupts) and the CPC (wait states that round every access to 4 cycles). Commercial games were mostly hand-written assembly. BASIC appears in loaders and in budget and type-in games. Tape was the main medium in the UK and Europe, disk in the US and Japan, and cartridge on the MSX, VIC-20 and Atari.

### Sinclair ZX81 and ZX Spectrum

The **ZX81** launched in the UK on 5 March 1981 at £69.95 assembled and sold over 1.5 million. Its CPU generates the display, so FAST mode blanks the screen to run faster. Tape runs at roughly 250–300 bit/s ([Wikipedia: ZX81](https://en.wikipedia.org/wiki/ZX81)). Its tape encoding differs from the Spectrum's, so TZX does not describe it natively ([TZX format](https://worldofspectrum.net/TZXformat.html)).

The **48K Spectrum** launched on 23 April 1982. The 128K followed in Spain in September 1985 and the UK in January 1986, then Amstrad's +2 (1986), +3 (1987) and +2A (late 1988) ([Wikipedia: ZX Spectrum](https://en.wikipedia.org/wiki/ZX_Spectrum)). The 48K map puts ROM at 0x0000–0x3FFF, the screen bitmap at 0x4000–0x57FF and attributes at 0x5800–0x5AFF (not confirmed) ([Sinclair Wiki](https://sinclair.wiki.zxnet.co.uk/wiki/ZX_Spectrum_48K)). On 128K models, port 0x7FFD selects the RAM page at 0xC000, the shadow screen, the ROM and a lock bit. The +2A/+3 add port 0x1FFD for all-RAM modes (not confirmed) ([Sinclair Wiki: ZX Spectrum 128](https://sinclair.wiki.zxnet.co.uk/wiki/ZX_Spectrum_128)).

**Contended memory is the Spectrum's timing trap. It differs by model.** On the 48K, 0x4000–0x7FFF is contended. The first contended cycle falls at T-state 14335 after the interrupt, with a delay pattern of 6,5,4,3,2,1,0,0 per 8 T-states, over 224 T-states per line. "Late timing" ULAs run one T-state later. On the 128K and +2, pages 1, 3, 5 and 7 are contended from T-state 14361 with 228 T-states per line. On the +2A/+3, pages 4 to 7 are contended only when MREQ is active, with pattern 7,6,5,4,3,2,1,0,0 from 14363 ([Sinclair Wiki: Contended memory](https://sinclair.wiki.zxnet.co.uk/wiki/Contended_memory)). Frames last 69888 T-states on the 48K and 70908 on the 128K, with one maskable interrupt per frame. Most games use IM 2 (not confirmed) ([World of Spectrum FAQ](https://worldofspectrum.org/faq/reference/48kreference.htm)). A port that must match frame timing needs these tables per model.

Spectrum tapes carried turbo and protected loaders such as Speedlock and Alkatraz, often a BASIC stub followed by machine code that decrypts the next stage (not confirmed) ([Sinclair Wiki: Tape protection schemes](https://sinclair.wiki.zxnet.co.uk/wiki/Tape_protection_schemes)). **TZX exists to preserve those loaders.** Revision 1.20 stores pilot, sync and bit timings in T-states at 3.5 MHz, along with pulse sequences, direct recordings and generalised symbol encodings. Block 0x10 is standard timing, 0x11 turbo, 0x13 a pulse sequence used by some protections, 0x15 a direct recording and 0x19 generalised data ([TZX format](https://worldofspectrum.net/TZXformat.html)). TAP holds only standard ROM-loader blocks. SNA and Z80 are snapshots, SZX stores fuller machine state, and RZX records input for replay (not confirmed) ([Sinclair Wiki: file formats](https://sinclair.wiki.zxnet.co.uk/wiki/Category:File_formats)). The +3 used 3-inch disks protected with non-standard sectors (not confirmed) ([CPCWiki: Copy protection](https://www.cpcwiki.eu/index.php/Copy_protection)).

**SkoolKit** reads TAP, TZX and PZX tapes and Z80 and SZX snapshots. It also plays RZX recordings. Its `tap2sna.py` simulates tape loading, and `trace.py` traces execution and can write AY output as WAV ([SkoolKit](https://skoolkit.ca/)). Its published disassemblies include Skool Daze, Back to Skool, Contact Sam Cruise, Manic Miner, Jet Set Willy, Hungry Horace and the 48K ROM ([SkoolKit disassemblies](https://skoolkit.ca/disassemblies/)). Fuse ([fuse-emulator.sourceforge.net](https://fuse-emulator.sourceforge.net/)), ZEsarUX ([github.com/chernandezba/zesarux](https://github.com/chernandezba/zesarux)) and SpecEmu ([specemu.zxe.io](http://www.specemu.zxe.io/)) have debuggers. EightyOne covers the ZX81 (debugger features not confirmed). Spectrum Computing ([spectrumcomputing.co.uk](https://spectrumcomputing.co.uk/)), World of Spectrum ([worldofspectrum.org](https://worldofspectrum.org/)) and the Sinclair Wiki ([sinclair.wiki.zxnet.co.uk](https://sinclair.wiki.zxnet.co.uk/)) are the community references.

### BBC Micro and Acorn Electron

The Model A and B arrived on 1 December 1981, the B+ in mid-1985 and the Master in 1986. The MOS sits in a 16 KB ROM, last official version OS 1.2, with four 16 KB sideways ROM sockets expandable to sixteen. Video uses a 6845 CRTC for modes 0–6 and the SAA5050 for Teletext mode 7 ([Wikipedia: BBC Micro](https://en.wikipedia.org/wiki/BBC_Micro)). ROMSEL at &FE30 pages a ROM into &8000–&BFFF, with the MOS at &C000–&FFFF and SHEILA I/O at &FE00 (not confirmed) ([BeebWiki: Paged ROM](https://beebwiki.mdfs.net/Paged_ROM)). The B+ moved from the Intel 8271 disk controller to the WD1770, which broke some software ([Wikipedia: BBC Micro](https://en.wikipedia.org/wiki/BBC_Micro)). That change explains many disk-protection failures across models. The Electron's RAM is 4 bits wide, so the CPU drops to an effective 1 MHz or less when it touches RAM. It has no mode 7 and one sound channel (not confirmed) ([Wikipedia: Acorn Electron](https://en.wikipedia.org/wiki/Acorn_Electron)). UEF is the chunked tape format. SSD and DSD are DFS sector images (not confirmed) ([BeebWiki: UEF](https://beebwiki.mdfs.net/Uniform_Emulator_Format)).

The BBC has the best documented 8-bit game code anywhere. **Mark Moxon's "Elite on the 6502"** documents the BBC Micro, Electron, Master, C64, Apple II and NES versions, with about 130 deep dives ([bbcelite.com](https://www.bbcelite.com/)). Ian Bell's site hosts the original BBC source discs (not confirmed) ([iancgbell.clara.net/elite](http://www.iancgbell.clara.net/elite/)). b-em ([github.com/stardot/b-em](https://github.com/stardot/b-em)), BeebJit ([github.com/scarybeasts/beebjit](https://github.com/scarybeasts/beebjit)) and B2 ([github.com/tom-seddon/b2](https://github.com/tom-seddon/b2)) have debuggers, and Elkulator covers the Electron. Stardot ([stardot.org.uk](https://stardot.org.uk/forums/)) and BeebWiki ([beebwiki.mdfs.net](https://beebwiki.mdfs.net/)) are the community references.

### Commodore VIC-20 and C64

The **VIC-20** appeared in Japan in 1980 and worldwide in 1981 at US$299.95. It was the first computer to sell a million and many titles were ROM cartridges ([Wikipedia: VIC-20](https://en.wikipedia.org/wiki/Commodore_VIC-20)). Its VIC chip comes as the 6560 (NTSC) and 6561 (PAL), at 1.0227 and 1.1087 MHz (not confirmed) ([Wikipedia: MOS VIC](https://en.wikipedia.org/wiki/MOS_Technology_VIC)).

The **C64** was shown at CES in January 1982 and sold from August 1982. The 6510's on-chip port at $01 switches the BASIC, KERNAL and character ROMs and the $D000 I/O area in and out. Cartridges auto-start on the "CBM80" signature at $8000 ([Wikipedia: Commodore 64](https://en.wikipedia.org/wiki/Commodore_64)). BASIC sits at $A000–$BFFF, I/O or character ROM at $D000–$DFFF and KERNAL at $E000–$FFFF. The VIC-II is at $D000, the SID at $D400 and the CIAs at $DC00 and $DD00, and CIA 2 selects the VIC-II's 16 KB bank (not confirmed) ([C64 Wiki: Memory Map](https://www.c64-wiki.com/wiki/Memory_Map)). **Which ROMs and I/O are visible depends on $01 and on cartridge lines**, so a disassembly must record the bank state for each code region. The PAL VIC-II (6569) has 312 lines of 63 cycles, 19656 cycles per frame at 50.12 Hz. The NTSC 6567 has 263 lines of 65 cycles, or 262 of 64 on the early R56A. Badlines steal 40 cycles every eighth line (not confirmed) ([Christian Bauer, The MOS 6567/6569 VIC-II](https://www.zimmers.net/cbmpics/cbm/c64/vic-ii.txt)). The two SID revisions differ audibly, mainly in the filter (not confirmed) ([Wikipedia: SID](https://en.wikipedia.org/wiki/MOS_Technology_6581)). PAL and NTSC versions of C64, VIC-20 and Atari games are often separate builds for this reason.

**The 1541 drive has its own 6502 and ROM** ([Wikipedia: Commodore 64](https://en.wikipedia.org/wiki/Commodore_64)). Fast loaders and disk protections run custom code on the drive. Novaload, Freeload, Cyberload and Vorpal are fast loaders. Protections use bad sectors, half tracks and density changes (not confirmed) ([Codebase64](https://codebase64.org/)). PRG files carry a 2-byte load address. T64 is a tape container, C64 TAP holds raw pulse lengths, D64 is a 683-sector image of 174,848 bytes, G64 is a GCR track image that keeps protection, and CRT carries a cartridge hardware type (not confirmed) ([VICE manual: file formats](https://vice-emu.sourceforge.io/vice_17.html)). VICE has a monitor with breakpoints and a remote monitor protocol ([vice-emu.sourceforge.io](https://vice-emu.sourceforge.io/)), and CCS64 runs on Windows. Codebase64 and C64-Wiki ([c64-wiki.com](https://www.c64-wiki.com/)) are the community references.

### Amstrad CPC

The 464 arrived in June 1984, the 664 in April 1985 and the 6128 in mid-1985, with the Plus range and GX4000 in September 1990. Its Z80A runs at 4 MHz but wait states give about 3.3 MHz. Modes are 160x200 in 16 colours, 320x200 in 4 and 640x200 in 2, at 50 Hz. Disks are 3-inch, typically 180 KB per side ([Wikipedia: Amstrad CPC](https://en.wikipedia.org/wiki/Amstrad_CPC)). Every instruction is stretched to a multiple of 4 T-states, the "NOP time" of 1 microsecond (not confirmed) ([CPCWiki: CPU timing](https://www.cpcwiki.eu/index.php/Z80)). CRTC types 0 to 4 differ at the edges, which matters for split screens and overscan (not confirmed) ([CPCWiki: CRTC](https://www.cpcwiki.eu/index.php/CRTC)). The gate array interrupts every 52 lines, six times a frame (not confirmed) ([CPCWiki: Gate Array](https://www.cpcwiki.eu/index.php/Gate_Array)). CPC tapes use the TZX structure as .CDT with timings scaled by 4/3.5 ([TZX format](https://worldofspectrum.net/TZXformat.html)). Extended DSK stores per-sector size and status, so it keeps many protections (not confirmed) ([CPCWiki: DSK format](https://www.cpcwiki.eu/index.php/Format:DSK_disk_image_file_format)). WinAPE ([winape.net](http://www.winape.net/)) and Caprice32 ([github.com/ColinPitrat/caprice32](https://github.com/ColinPitrat/caprice32)) have debuggers, and CPCWiki ([cpcwiki.eu](https://www.cpcwiki.eu/)) is the community reference.

### MSX

ASCII announced MSX on 16 June 1983, and the first machine went on sale on 21 October 1983. MSX2 followed in 1985 and MSX2+ in 1988, in Japan only. MSX2 memory reaches 4 MB per slot through a memory mapper. Konami's SCC chip shipped inside some cartridges and adds five channels ([Wikipedia: MSX](https://en.wikipedia.org/wiki/MSX)). European machines use the TMS9929A (not confirmed) ([MSX Wiki](https://www.msx.org/wiki/)). Slots and subslots are selected through the PPI at port A8h and register FFFFh. VRAM is reached only through VDP ports 98h and 99h (not confirmed) ([MSX Wiki: Slots](https://www.msx.org/wiki/Slots)). **MegaROM cartridges use bank-switching mappers** (Konami, Konami SCC, ASCII 8K, ASCII 16K). An emulator needs the right mapper type to run a dump (not confirmed) ([MSX Wiki: MegaROM mappers](https://www.msx.org/wiki/MegaROM_Mappers)). Images are ROM dumps with a mapper type, DSK and CAS (not confirmed) ([openMSX manual](https://openmsx.org/manual/)). openMSX has a Tcl console and a separate debugger ([openmsx.org](https://openmsx.org/)). The MSX Resource Center is at [msx.org](https://www.msx.org/).

### Atari 400/800, XL and XE

The 400 and 800 shipped in November 1979, the XL range from 1983 and the XE range from 1985. ANTIC runs a display list with one instruction per mode line, CTIA or GTIA does colour and player/missile graphics. POKEY does sound, keyboard and serial I/O ([Wikipedia: Atari 8-bit](https://en.wikipedia.org/wiki/Atari_8-bit_computers)). Banking on the 130XE uses PIA PORTB at $D301 with a 16 KB window at $4000. Display list interrupts are enabled through NMIEN, and ANTIC DMA steals cycles on each line (not confirmed) ([Altirra Hardware Reference Manual](https://www.virtualdub.org/altirra.html)). ATR is a sector image, XEX a DOS executable, CAS a tape and ATX a protected-disk image with timing and weak sectors (not confirmed). Altirra has a debugger and ships its own hardware reference ([virtualdub.org/altirra.html](https://www.virtualdub.org/altirra.html)). AtariAge is the community hub ([atariage.com](https://atariage.com/)).

### Dragon 32/64, CoCo and Oric

The CoCo was announced in July 1980 at US$399 with a 6809E and an MC6847 VDG. The CoCo 3 (1986–1991) adds the GIME, a 64-colour palette and double speed. OS-9 ran on it ([Wikipedia: TRS-80 Color Computer](https://en.wikipedia.org/wiki/TRS-80_Color_Computer)). The Dragon 32 arrived in August 1982 with a 0.89 MHz 6809E, and Dragon Data collapsed in 1984 ([Wikipedia: Dragon 32/64](https://en.wikipedia.org/wiki/Dragon_32/64)). Both use the MC6883 SAM for memory and timing and a 6-bit DAC for sound, and a "speed-up poke" doubles the clock on some machines (not confirmed) ([Dragon Wiki](https://archive.worldofdragon.org/)). XRoar emulates both ([6809.org.uk/xroar](https://www.6809.org.uk/xroar/)). World of Dragon is the community site ([worldofdragon.org](https://worldofdragon.org/)).

The Oric-1 launched on 1 September 1982 and the Atmos on 1 February 1984. Its serial attributes take one character cell each. **Some games depend on BASIC ROM v1.0**, so the ROM version is part of the ground truth ([Wikipedia: Oric](https://en.wikipedia.org/wiki/Oric_(computer))). A 6522 VIA drives the AY, keyboard, printer and tape (not confirmed) ([Defence Force Oric wiki](https://wiki.defence-force.org/)). Oricutron is the emulator ([github.com/pete-gordon/oricutron](https://github.com/pete-gordon/oricutron)). Defence Force is the community site ([defence-force.org](https://www.defence-force.org/)).

### Apple II

The Apple II went on sale on 10 June 1977. Hi-res mode is 280x192 with six visible colours. The speaker is a 1-bit toggle. Disk II and Apple DOS arrived in late 1978 with 140 KB per side ([Wikipedia: Apple II (original)](https://en.wikipedia.org/wiki/Apple_II_(original))). The IIgs (1986) uses the 65C816, and about six million Apple IIs were sold ([Wikipedia: Apple II](https://en.wikipedia.org/wiki/Apple_II)). The speaker toggles at $C030, soft switches fill $C000–$C0FF and the language card banks RAM over $D000–$FFFF. The IIgs runs at 2.8 MHz with an Ensoniq 5503 DOC (not confirmed) ([AppleWin](https://github.com/AppleWin/AppleWin); [Wikipedia: Apple IIGS](https://en.wikipedia.org/wiki/Apple_IIGS)). Disk II encoding is software-controlled GCR, so publishers wrote custom sector formats, nibble counts and spiral tracks. **WOZ keeps bit-level tracks and timing so protected disks run**, while DSK, DO and PO keep only 140 KB of sectors (not confirmed) ([WOZ reference](https://applesaucefdc.com/woz/reference2/)). Jordan Mechner released the Apple II Prince of Persia source in 2012 (not confirmed) ([github.com/jmechner/Prince-of-Persia-Apple-II](https://github.com/jmechner/Prince-of-Persia-Apple-II)).

### NEC PC-8801 and Sharp X1

The PC-8801 shipped in November 1981 and ran N88-BASIC. With the FM-7, X1 and MSX it was one of Japan's four major home computers, and Ys, Thexder, Snatcher and the Dragon Slayer series first appeared on it ([Wikipedia: PC-8800 series](https://en.wikipedia.org/wiki/PC-8800_series)). The X1 launched in 1982 and the X1 turbo in 1984 (not confirmed) ([Wikipedia: Sharp X1](https://en.wikipedia.org/wiki/Sharp_X1)). ### What this means for an exact reimplementation

The first job on a tape or disk game is usually to get past the loader. Run it under an emulator until the game code sits in memory, then snapshot. Protection code belongs to the original's behaviour only until the game starts, so a reimplementation normally begins from the decrypted in-memory image. Keep the lossless media image (TZX, G64, WOZ, EDSK, ATX) as the record of what shipped. The VICE remote monitor, openMSX's Tcl console, MAME's Lua scripting and the ZEsarUX remote protocol suit agent-driven capture best, because a script can drive them. The Elite and SkoolKit projects show the useful end product, a source that reassembles byte for byte to the original and so gives an exact oracle for any port. Whether those disassemblies include game bytes, and under what licence, still needs checking, which matters under a "no game material" rule. The cross-assemblers that studios used lack a primary source.

## Sixteen and 32-bit computers put the custom chips in charge

Three CPU families run these machines. The Amiga, Atari ST and X68000 use the big-endian 68000 line, the Archimedes and Risc PC use ARM, and the PC-98 and FM Towns use x86. **Each machine's custom video and sound chips shape how its games were written**, and many Amiga and ST games skip the OS and drive those chips directly. A game that uses the OS (GEM, AmigaOS libraries, RISC OS SWIs, Human68k or MS-DOS calls) can be traced at the OS call boundary. Trace a takeover game at its hardware register writes. The port must rebuild the chips' behaviour. No source gives a count of OS-friendly against takeover games.

### Commodore Amiga

**Agnus** is the chip RAM DMA controller. It arbitrates between the CPU and the custom chips and holds the Blitter and the Copper. The original Agnus addresses 512 KB of chip RAM, and later "Fat Agnus" revisions raised this to 1 MB and then 2 MB. Timing runs in 280 ns colour clocks. The **Blitter** combines up to three sources into a destination over blocks up to 1,024x1,024 pixels. The **Copper** runs a three-instruction program (MOVE, WAIT, SKIP) synchronised to the beam and restarts every frame, so raster effects come from a per-frame Copper list. **Denise** gives 1 to 5 bitplanes for 2 to 32 colours from 4,096, plus Extra-Halfbrite and HAM with a sixth plane, and eight 16-pixel sprites. **Paula** handles interrupts, four 8-bit DMA audio channels, the floppy and the serial port. Audio DMA peaks at about 28,867 samples/s per channel on NTSC and 28,837 on PAL. Displays are 200 lines on NTSC and 256 on PAL ([Wikipedia: Original Chip Set](https://en.wikipedia.org/wiki/Original_Chip_Set)). That article asks for more citations, so the Amiga Hardware Reference Manual should confirm Copper, sprite and HAM details. Exact PAL and NTSC CPU clocks also need that manual.

An OCS game built for 512 KB of chip RAM behaves differently from an ECS or AGA build, so record the model and Kickstart version with every capture. A takeover game ties its timing to the vertical blank, 50 Hz on PAL and 60 Hz on NTSC. A port must pick one.

Amiga disks need care. **Plain ADF sector images cannot hold most copy protection.** The Software Preservation Society's IPF format begins with "CAPS", holds low-level track data, is often made from KryoFlux captures, and has an open-source library ([Wikipedia: Amiga Disk File](https://en.wikipedia.org/wiki/Amiga_Disk_File); [IANA: IPF](https://www.iana.org/assignments/media-types/application/vnd.softpres-ipf-disk-image)). SPS notes that the Amiga's free-form track format rules out automatic format scripting ([SPS news 2005-08-05](https://softpres.org/news:2005-08-05)). Rob Northen's **Copylock** protected disks on the Amiga, ST and PC. Its trace vector decoder decrypts each instruction, runs it, then encrypts it again ([Wikipedia: Rob Northen copylock](https://en.wikipedia.org/wiki/Rob_Northen_copylock); [Wikipedia: Trace vector decoder](https://en.wikipedia.org/wiki/Trace_vector_decoder)). CAPS reverse engineered the Amiga Copylock in June 2001 and counted over 500 titles using it ([SPS Copylock Unlocked](https://softpres.org/wip:2001-06-07); [Part 2](https://softpres.org/wip:2001-06-08)). SPS also supports Copylock ST and Speedlock timing tracks ([SPS 2002-10-28](https://softpres.org/wip:2002-10-28); [SPS Speedlock](https://softpres.org/wip:2003-06-01)). Later keydisks carried a unique serial number in the disk format ([Codetapper interview with Rob Northen](https://codetapper.com/amiga/interviews/rob-northen)). A self-decrypting game is best read after decryption, from emulator memory.

For static analysis, **BartmanAbyss/ghidra-amiga** loads hunk executables, Kickstart ROMs and WinUAE state files with NDK 3.9 symbols. It is forked from lab313ru's ghidra_amiga_ldr and builds on work by Vladimir Kononovich and Martin Atkins ([BartmanAbyss on GitHub](https://www.github.com/BartmanAbyss); [amiga-news 2022](https://amiga-news.de/en/news/AN-2022-09-00023-EN.html)). A 2023 update targeted Ghidra 10.3.1 ([amiga-news 2023](https://amiga-news.de/en/news/AN-2023-06-00122-EN.html)). One user reports that the Ghidra 12.0.1 build loaded in 12.1.3 only after editing its version line ([Sebastian Bergmann](https://amiga.sebastian-bergmann.de/2026/08/29/disassembling-my-1994-self/)). The same author wrote a Mega Drive loader ([spritesmind forum](https://gendev.spritesmind.net/forum/viewtopic.php?p=38020)), and amitools' Python hunk library also loads hunk binaries ([lab313ru/amitools_dbg](https://github.com/lab313ru/amitools_dbg)). Unicorn runs the 68000 code but none of the custom chips.

WinUAE has a debugger opened with Shift+F12, and `fp "name"` runs until a named process starts ([markwrobel.dk](https://markwrobel.dk/post/amiga-machine-code-part1-debugger)). It supports memory watchpoints, and the VS Code Amiga extension can step Copper lists through FS-UAE ([vscode-amiga-assembly wiki](https://github-wiki-see.page/m/prb28/vscode-amiga-assembly/wiki/Debugging-emulator)). MAME's debugger also has watchpoints ([MAME docs](https://docs.mamedev.org/debugger/watchpoint.html)). vAmiga's debugger is not documented here.

Amiga reimplementations took several routes. **rawgl** by cyxx reimplements the Another World engine and reads Amiga, Atari, DOS, Windows 3.1, 3DO and anniversary data; it was archived on 28 June 2025 ([cyxx/rawgl](https://github.com/cyxx/rawgl)). **OpenFodder** is a GPL-3.0 engine for Cannon Fodder 1 and 2 on Amiga, CD32 and DOS CD. Its README does not say how it was made ([OpenFodder](https://github.com/OpenFodder/openfodder)). **pyDM** is a Python port of Amiga Dungeon Master built from the ReDMCSB Amiga V3.x branch ([pyDM](https://codeberg.org/CyCl0ne/pyDM)).

### Atari ST family

The 520ST shipped in June 1985 with an 8 MHz 68000, a YM2149, an MFP and a WD-1772. The Shifter gives 320x200 in 16 colours and 640x200 in 4 from 512, plus 640x400 mono at 71.2 Hz. The STE (late 1989) adds a Blitter, fine scrolling, split screen and 8-bit stereo DMA PCM. The Falcon030 (1992) adds a Motorola 56001 DSP ([Wikipedia: Atari ST](https://en.wikipedia.org/wiki/Atari_ST)). The .ST image is raw data with no metadata and no protection. MSA adds a geometry header and RLE. **STX (Pasti) stores non-standard sectors, fake track addresses and sector timing** ([fplanque.com](https://www.fplanque.com/tech/retro/atari/atari-st-fd-image-file-formats/); [8bitchip forum](https://forum.8bitchip.info/atari-faq/disk-imaging-popular-formats/)). Its author never documented STX, and Hatari 1.8.0 (2014) added the first open-source decoder ([IANA: Pasti STX](https://www.iana.org/assignments/media-types/application/vnd.pasti-stx-disk-image); [st-computer.org](https://en.st-computer.org/news/2014/07/06/hatari-1-8-0-supports-pasti/)).

**Hatari has the best documented debugger of these machines.** It offers conditional breakpoints with up to four conditions, CPU and DSP disassembly, symbol loading, profiling with Callgrind output, and tracing of GEMDOS, BIOS, XBIOS, AES and VDI calls. Command scripts can run at startup and on breakpoints ([Hatari debugger manual](https://hatari.tuxfamily.org/doc/debugger.html)). No Ghidra loader for ST PRG files is known. Steem SSE's debugger is not documented here.

The ST is the source of two notable projects. In **glFrontier**, Tom Morton started from the ST version of Frontier: Elite II, stripped the hardware access from the assembly and changed a 68k assembler to emit C or i386 assembly ([virtuallyfun.com](https://virtuallyfun.com/?p=59); [Aminet readme](https://se.aminet.net/game/actio/frontier-elite2-gl.aros.readme)). fe2-intro reproduces the Frontier intro ([watsonmw/fe2-intro](https://github.com/watsonmw/fe2-intro)). **ReDMCSB** is reconstructed Dungeon Master and Chaos Strikes Back source by forum user ChristopheF. Its build scripts make ST and Amiga executables, with an option to drop copy protection ([dungeon-master.com forum](https://www.dungeon-master.com/forum/viewtopic.php?p=163896)). DM/CSB version 3 was built with Think C on Apple hardware ([dungeon-master.com forum](https://www.dungeon-master.com/forum/viewtopic.php?p=162234)). ReDMCSB's binary-matching claims remain unconfirmed.

### Acorn Archimedes and Risc PC

The A305, A310 and A440 arrived in July 1987 with an 8 MHz ARM2 and Arthur. The A3000 (1989) brought RISC OS 2, the A5000 (1991) an ARM3 at 25 or 33 MHz, and the A3010 range (1992) the ARM250, which merges ARM2, IOC, VIDC and MEMC on one chip. VIDC1 gives eight channels of 8-bit logarithmic stereo sound. The A5000 was the first with an HD drive and reads MS-DOS and ST disks ([Wikipedia: Acorn Archimedes](https://en.wikipedia.org/wiki/Acorn_Archimedes)). The Risc PC launched on 15 April 1994 with VIDC20 video and CPUs up to a 300 MHz StrongARM ([Wikipedia: Risc PC](https://en.wikipedia.org/wiki/Risc_PC)). **ARM2 and ARM3 use the 26-bit address mode with flags in R15**, and Risc PC CPUs added 32-bit mode. Ghidra's ARM languages start at v4 and QEMU-based Unicorn likely lacks 26-bit mode, so Archimedes code may need a 26-bit-aware emulator such as Arculator. Archimedes disk image formats, RISC OS module loaders for Ghidra, and the debuggers of Arculator and RPCEmu still need sources.

### Sharp X68000

The X68000 was released in March 1987 in Japan only. Its 1056 KB of VRAM splits into graphics, text and sprite areas. It shows 128 sprites, 32 per line, and raster interrupts can raise that to 512. Sound is a YM2151 with eight FM channels and an MSM6258 ADPCM channel at 15.6 kHz. Human68k is an MS-DOS-like OS made by Hudson Soft. Floppies hold 77 tracks of 8 sectors of 1024 bytes at 360 rpm ([Wikipedia: X68000](https://en.wikipedia.org/wiki/X68000)). The XDF, DIM and HDM image formats and the XM6, PX68k and Unz debuggers still need sources. MAME is the fallback debugger.

### NEC PC-9801 and Fujitsu FM Towns

The PC-9801 launched in October 1982. Its two μPD7220 controllers handle text and graphics separately, at 640x400 in 8 colours and later 16 from 4,096. The GRCG and EGC blitters arrived in 1985 and 1986, and FM sound came on the PC-9801-26 card (YM2203) and the PC-9801-86 (YM2608). NEC shipped 18.3 million units before ending the line on 30 September 2003 ([Wikipedia: PC-98](https://en.wikipedia.org/wiki/PC-98)). The PC-98 runs x86 code under MS-DOS, but its display and sound hardware differ from the IBM PC's. GameFrame's DOS tools therefore help with the CPU and DOS layer. The hardware layer needs its own notes. Floppy images come as FDI, FDD, D88/D98, HDM and NFD, and hard disks as HDI and NHD. Neko Project II Kai needs BIOS, font and sound ROMs ([libretro: Neko Project II Kai](https://docs.libretro.com/library/neko_project_ii_kai/); [Batocera wiki](https://wiki.batocera.org/systems:pc98)).

The FM Towns was released on 28 February 1989 with a 16 MHz 386DX and a CD-ROM drive as standard. About 500,000 were sold. Towns OS is MS-DOS with the Phar Lap DOS extender, and the FM Towns Marty console (1993) runs Towns games ([Wikipedia: FM Towns](https://en.wikipedia.org/wiki/FM_Towns)). Towns games built on the Phar Lap extender need a loader for extended DOS programs, which differs from a real-mode MZ load.

### What this means for an exact reimplementation

Data files that moved between platforms can change byte order, since the 68000 machines are big-endian and the ARM and x86 machines little-endian. A port of a takeover game reproduces the Copper list, the Blitter operations and the audio DMA at the frame rate of one TV standard. Ground truth for a single function can come from Unicorn's 68000 when the function touches only RAM. Anything that reads chip registers needs a full emulator trace from Hatari, WinUAE or MAME. The Sinclair QL (68008) and SAM Coupé (Z80B) belong in this family but still need sources.

## The PC and Mac change executable format with every era

On the PC and Mac the CPU barely changes the method. The executable format does. **Each PC era has its own executable format and tool chain.** DOS used COM and MZ, Win16 used NE, DOS extenders used LE and LX, Win32 used PE32 and x64 uses PE32+. Checking the magic (MZ, then the header at e_lfanew for NE, LE, LX or PE) is the first triage step, and GameFrame's `tools/triage` and `tools/dos` already cover MZ and NE. The Mac has had four CPU families, each with its own wrapper. The practical break for study is that **64-bit Windows cannot run 16-bit code** and **macOS since Catalina cannot run 32-bit apps**, so most older games now run only in an emulator or on old hardware.

The **PCjr and Tandy 1000** matter because some games detect Tandy hardware and draw Tandy graphics even when CGA is chosen ([Tandy Graphics Adapter](https://en.wikipedia.org/wiki/Tandy_Graphics_Adapter)). Sierra's King's Quest (1984) was commissioned by IBM for the PCjr (not confirmed) ([King's Quest I](https://en.wikipedia.org/wiki/King%27s_Quest_I)). A Tandy path is a separate rendering and sound path in the same binary, so an exact port must choose which path is ground truth.

In the **Win16** era, WinG shipped on 21 September 1994 to let Windows 3.x programs write bitmap memory directly. It helped port DOS games and was later replaced by DirectX and CreateDIBSection. Doom95, SimCity 2000, SimTower and Civilization II are among the games listed as using it ([WinG](https://en.wikipedia.org/wiki/WinG)). Microsoft states that "64-bit Windows does not support running 16-bit Windows-based applications". Such attempts fail with ERROR_BAD_EXE_FORMAT. WOW64 runs 32-bit code on x64 and ARM64, but a 32-bit process cannot load a 64-bit DLL for execution ([Running 32-bit Applications, Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winprog64/running-32-bit-applications)). Windows 11 has no 32-bit edition, so no current Windows runs 16-bit code (not confirmed) ([Virtual DOS machine](https://en.wikipedia.org/wiki/Virtual_DOS_machine); [Windows 11](https://en.wikipedia.org/wiki/Windows_11)). Steam launched in September 2003 and GOG in 2008, and GOG often repackages old games with DOSBox or ScummVM (not confirmed) ([Steam (service)](https://en.wikipedia.org/wiki/Steam_(service)); [GOG.com](https://en.wikipedia.org/wiki/GOG.com)).

**The compiler identifies itself in the binary.** Knowing it tells a port which library code to skip and which arithmetic rules to copy. These fingerprints are widely documented, though each one below is (not confirmed). Turbo Pascal programs fail with "Runtime error 200" on fast CPUs because the CRT unit's delay calibration divides by zero ([Turbo Pascal](https://en.wikipedia.org/wiki/Turbo_Pascal); [Runtime error 200](https://en.wikipedia.org/wiki/Turbo_Pascal#CRT_Delay_problem)). Borland C++ leaves a copyright string, its c0.asm startup code and sometimes appended TDInfo debug data ([Borland C++](https://en.wikipedia.org/wiki/Borland_C%2B%2B)). Watcom bundled DOS/4GW, which prints a start-up banner. Its default 32-bit convention passes arguments in EAX, EDX, EBX and ECX; Doom was built with it ([Watcom C/C++](https://en.wikipedia.org/wiki/Watcom_C/C%2B%2B); [DOS/4G](https://en.wikipedia.org/wiki/DOS/4G)). Quake was built with DJGPP ([DJGPP](https://en.wikipedia.org/wiki/DJGPP)). MSVC-linked PE files carry the undocumented "Rich" header and import CRTs such as MSVCRT.DLL or VCRUNTIME140.DLL ([Microsoft Visual C++](https://en.wikipedia.org/wiki/Microsoft_Visual_C%2B%2B)). Delphi binaries carry VCL class names, RTTI and DFM form resources ([Delphi](https://en.wikipedia.org/wiki/Delphi_(software))). .NET assemblies decompile to near-source C# ([.NET Framework](https://en.wikipedia.org/wiki/.NET_Framework); [Mono](https://en.wikipedia.org/wiki/Mono_(software))). Unity's IL2CPP "converts all managed assemblies into standard C++ code" compiled to an executable or DLL ([IL2CPP overview, Unity Manual](https://docs.unity3d.com/Manual/il2cpp-introduction.html)). On Windows that output is GameAssembly.dll plus global-metadata.dat, from which Il2CppDumper rebuilds names (not confirmed) ([Il2CppDumper](https://github.com/Perfare/Il2CppDumper)).

**Protection checks moved over the years toward the disc and later to online activation.** Manual checks and code wheels such as Monkey Island's "Dial-a-Pirate" came first, with malformed floppy tracks alongside (not confirmed) ([Copy protection](https://en.wikipedia.org/wiki/Copy_protection)). SafeDisc appeared in 1998 and was discontinued in March 2009. Its secdrv.sys driver had a privilege flaw patched in December 2007, and Microsoft said in 2015 that SafeDisc games would not run on Windows 10. SecuROM games would not run there either ([SafeDisc](https://en.wikipedia.org/wiki/SafeDisc)). StarForce 3.0 installed a driver that stayed after uninstall. In 2006 Heroes of Might and Magic V and GTR2 replaced it with SecuROM ([StarForce](https://en.wikipedia.org/wiki/StarForce)). Valve says the Steam DRM wrapper "by itself is not an anti-piracy solution" and is "easily removed by a motivated attacker" ([Steam DRM, Steamworks documentation](https://partner.steamgames.com/doc/features/drm)). Denuvo's first game was FIFA 15 in September 2014. It needs online activation, binds a token to the hardware and is integrated with the game's code. Publishers have removed it by patch ([Denuvo](https://en.wikipedia.org/wiki/Denuvo)). Protected or virtualised regions resist decompilation, so Unicorn emulation works best on the game's own logic. Later DRM-free releases are often the cleanest owned copy to study. The legal position on bypassing protection varies by country, as `docs/LEGAL.md` describes. The choice of route stays with the user.

Engine-era games move the logic. Unreal Engine 4 and 5 pack assets in .pak files that may be AES-encrypted. UObject reflection keeps class names in the binary (not confirmed) ([Unreal Engine](https://en.wikipedia.org/wiki/Unreal_Engine)). Godot packs .pck files, and gdsdecomp recovers projects (not confirmed) ([Godot](https://godotengine.org/); [gdsdecomp](https://github.com/bruvzg/gdsdecomp)). Kernel-level anti-cheat can block debuggers (not confirmed) ([Anti-cheat software](https://en.wikipedia.org/wiki/Anti-cheat_software)). Linux ports came from Loki Software between 1998 and 2002. Linux play now runs mostly through Proton (2018) and the Steam Deck (2022) (not confirmed) ([Loki Entertainment Software](https://en.wikipedia.org/wiki/Loki_Entertainment_Software); [Proton](https://en.wikipedia.org/wiki/Proton_(software)); [Steam Deck](https://en.wikipedia.org/wiki/Steam_Deck)). Linux builds sometimes keep more symbols than Windows builds, which makes them a useful second binary.

Ghidra has built-in loaders for MZ, NE, PE and Mach-O, and LE/LX needs a community extension (not confirmed) ([Ghidra file formats overview](https://www.mintlify.com/NationalSecurityAgency/ghidra/processors/file-formats)).

### Macintosh eras

| Era | Years | CPU | Code format | Emulator |
|---|---|---|---|---|
| 68k Classic Mac OS | 1984–1998 (Mac OS 8.1 is the last 68k release) | 68000, 68020, 68030, 68040 | CODE resources in the resource fork, A5 world, A-line traps | Mini vMac, MAME, Basilisk II |
| PowerPC Classic and early OS X | 1994–2006 | 601 to G5 | PEF loaded by the Code Fragment Manager; fat apps carry both | SheepShaver, QEMU |
| Intel | 2006–2020 | x86, x86-64 | Mach-O, universal binaries | Native, VMs |
| Apple silicon | 2020 on | ARM64 | Mach-O | Native; Rosetta 2 for x86-64 |

The Macintosh 128K arrived on 24 January 1984, the Mac II in March 1987 and the Quadra 700/900 in October 1991 (not confirmed) ([Macintosh 128K](https://en.wikipedia.org/wiki/Macintosh_128K); [Macintosh II](https://en.wikipedia.org/wiki/Macintosh_II); [Macintosh Quadra](https://en.wikipedia.org/wiki/Macintosh_Quadra)). Mac OS 8.1 (January 1998) was the last 68k-compatible release ([Basilisk II](https://en.wikipedia.org/wiki/Basilisk_II)). **68k application code lives as CODE resources in the resource fork.** CODE 0 holds the jump table, globals and the jump table sit around register A5, the Segment Loader loads segments on demand. Toolbox calls are A-line traps (not confirmed) ([Inside Macintosh: Mac OS Runtime Architectures](https://developer.apple.com/library/archive/documentation/mac/runtimehtml/RTArch-110.html)). Ghidra does not understand resource forks. Users open a fork on macOS by adding `..namedfork/rsrc` to the path, import CODE resources as raw binaries and add A-trap names to the 68000 spec by hand. RetroGhidra has a basic Classic Mac loader ([A-Traps in Ghidra, 68kMLA](https://68kmla.org/bb/goto/post?id=466137); [68kmla.org thread](https://68kmla.org/bb/goto/post?id=510430)). Forks are lost on non-Mac file systems, so archives use MacBinary, BinHex, AppleSingle/AppleDouble or DiskCopy images (not confirmed) ([Resource fork](https://en.wikipedia.org/wiki/Resource_fork)). A 68k Mac binary therefore needs three steps before analysis: extract the fork, split the CODE resources and rebuild the A5 jump table. No mainstream loader does all three. resource_dasm decodes many classic resource types and disassembles 68k and PPC code resources (not confirmed) ([resource_dasm](https://github.com/fuzziqersoftware/resource_dasm)).

The first Power Macs launched on 14 March 1994 with a 68k emulator in ROM (not confirmed) ([Power Macintosh](https://en.wikipedia.org/wiki/Power_Macintosh)). **PEF** is Apple's RISC executable format for Classic Mac OS, loaded by the Code Fragment Manager and kept on PowerPC Mac OS X for Carbon apps ([Preferred Executable Format](https://en.wikipedia.org/wiki/Preferred_Executable_Format)). Ghidra ships a PEF loader ([Ghidra API: PefLoader 11.4](https://ghidradocs.com/11.4_PUBLIC/docs/GhidraAPI_javadoc/api/ghidra/app/util/opinion/PefLoader.html); [PefLoader 12.1.3](https://ghidradocs.com/12.1.3_PUBLIC/docs/GhidraAPI_javadoc/api/ghidra/app/util/opinion/PefLoader.html)). Fat Classic apps held 68k CODE resources and a PPC fragment together (not confirmed) ([Fat binary](https://en.wikipedia.org/wiki/Fat_binary)). The Classic environment ran Mac OS 9 apps up to 10.4 and never on Intel (not confirmed) ([Classic environment](https://en.wikipedia.org/wiki/Classic_Environment)). Intel Macs arrived in January 2006 (not confirmed) ([Mac transition to Intel processors](https://en.wikipedia.org/wiki/Mac_transition_to_Intel_processors)). Rosetta translated PowerPC code from 10.4.4 until Lion removed it in 2011 ([Rosetta](https://en.wikipedia.org/wiki/Rosetta_(software))). Mach-O magic is 0xfeedface or 0xfeedfacf. Universal files use 0xcafebabe ([Mach-O](https://en.wikipedia.org/wiki/Mach-O)). macOS Catalina (7 October 2019) ran only 64-bit apps ([macOS Catalina](https://en.wikipedia.org/wiki/MacOS_Catalina)). Rosetta 2 shipped with Big Sur. Apple said at WWDC 2025 that most of it will go in macOS 28 (2027), keeping support for older unmaintained games; the source disagrees with itself on 27 or 28 ([Rosetta](https://en.wikipedia.org/wiki/Rosetta_(software))). Rosetta 2 does not translate kernel extensions or AVX instructions (not confirmed) ([About the Rosetta translation environment, Apple](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)). A fat or universal file carries two compiled versions of the same game, which gives a second view of each function.

Basilisk II (GPL, 1999) emulates 68k Macs up to Mac OS 8.1 ([Basilisk II](https://en.wikipedia.org/wiki/Basilisk_II)). SheepShaver (GPL, final release 2.5 in September 2022) runs Mac OS 7.5.2 to 9.0.4 and has no MMU emulation ([SheepShaver](https://en.wikipedia.org/wiki/SheepShaver)). Mini vMac covers the Mac Plus era ([Mini vMac](https://www.gryphel.com/c/minivmac/)), QEMU's g3beige and mac99 run Mac OS 9 and OS X to 10.5 ([QEMU PowerPC Mac documentation](https://www.qemu.org/docs/master/system/ppc/powermac.html)), and MAME has Mac drivers ([MAME](https://www.mamedev.org/)) (all not confirmed). Executor and Advanced Mac Substitute reimplement the 68k Mac OS without Apple ROMs (not confirmed) ([Executor](https://en.wikipedia.org/wiki/Executor_(software)); [Advanced Mac Substitute](https://www.v68k.org/advanced-mac-substitute/)). Unicorn runs 68k and PowerPC code (not confirmed) ([Unicorn Engine](https://www.unicorn-engine.org/)). Single CODE-segment functions could run under Unicorn with the A5 world and the needed traps stubbed, much as `tools/emu/dos_env` stubs DOS.

Mac game history includes Myst (1993), built with HyperCard (not confirmed) ([Myst](https://en.wikipedia.org/wiki/Myst)), and Bungie's Marathon (1994) (not confirmed) ([Marathon](https://en.wikipedia.org/wiki/Marathon_(video_game))). Bungie released the Marathon 2 source in January 2000, and Aleph One grew from it. The trilogy's data became freeware in 2005, and "Classic Marathon 2" was re-released on Steam on Aleph One ([Marathon 2: Durandal](https://en.wikipedia.org/wiki/Marathon_2:_Durandal); [Aleph One on GitHub](https://github.com/Aleph-One-Marathon/alephone)). Aleph One is a fan engine grown from that source, so exact-match work should still use the shipped binary.

## Consoles outside the current pages span discrete logic to signed executables

The console pages already cover the NES to the GBA, the 32/64-bit consoles, the sixth generation and arcade boards. The remaining platforms fall into four groups. **The early consoles have tiny ROMs, no OS and well-known CPUs.** The 32-bit oddities and CD add-ons put real game code on co-processors. **From the Xbox 360 on, every platform ships signed and encrypted executables** in a vendor format (XEX, SELF, RPX, NSO), so a decrypted dump and the right loader come before any analysis. Ghidra's built-in processors cover most of these CPUs. Its processor list is the reference for the mapping below ([GitHub: ghidra/Ghidra/Processors](https://github.com/NationalSecurityAgency/ghidra/tree/master/Ghidra/Processors)).

The **Odyssey** cannot be reverse engineered as software. A "port" is a circuit simulation, closer to discrete-logic arcade games. On the **2600** there is no frame buffer. The program writes TIA registers in time with each scanline ("racing the beam"). **Timing is the game**, so a faithful rebuild must model cycles per scanline, and cycle-exact emulator traces are the ground truth. Stella has a debugger built on DiStella with breakpoints, TIA and RIOT views and scanline stepping (not confirmed) ([Stella](https://stella-emu.github.io/)). Commented 2600 disassemblies appear on AtariAge (not confirmed) ([AtariAge](https://atariage.com/)). The Intellivision's clock figure conflicts between sources. One gives about 894.886 kHz (the NTSC colour clock divided by 4) and the CPU article gives about 2 MHz for the CP1610 ([Wikipedia: CP1600](https://en.wikipedia.org/wiki/General_Instrument_CP1600)). Many Intellivision games call into the Executive ROM, so that ROM is part of the behaviour. jzIntv has a command-line debugger (not confirmed) ([jzIntv](http://spatula-city.org/~im14u2c/intv/)). MAME's debugger works across all these CPUs ([MAME docs: debugger](https://docs.mamedev.org/debugger/index.html)).

## Conclusion

The hardest platforms to port exactly are the oldest and the newest. The oldest make timing part of the game logic, with Spectrum contention, the 2600's scanline racing and the C64's badlines. The newest put encryption and per-platform loaders before the first instruction can be read. The middle generations are the easiest, because Ghidra and Unicorn both cover the 68000, ARM, MIPS, PowerPC and x86. That gap points to GameFrame's clearest next tool. Unicorn has no 8-bit core, and Ghidra's 6502 p-code gets ADC wrong. A small, permissively licensed 6502 and Z80 runner (py65, mos6502, iz80, floooh/chips or the BSD-licensed MAME cores) would give 8-bit games the same function-level ground truth that `tools/emu` gives DOS and Windows code. It would be tested against sample code GameFrame builds itself.

The second lesson is that the best existing 8-bit and 16-bit work already looks like GameFrame's target. Elite on the 6502, SkoolKit's disassemblies, ReDMCSB and glFrontier each turned shipped bytes into documented source that can be checked against the original. The PowerPC recompilers and the Galaxy decompilation show the same pattern on modern consoles. Several facts still need a second source, notably the 8-bit memory maps and chip timings, the Amiga CPU clocks, the PC-era dates and the 2026 emulator news. They keep the "(not confirmed)" mark until a primary source confirms them. Each emulator status carries its date.
